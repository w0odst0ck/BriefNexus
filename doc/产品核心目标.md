## 一、一句话定义

**BriefNexus 是信息采集的基建平台**：一个可挂载的 HTTP 服务公共平台——内置信息采集器与路由表，任何应用即连即用，数据永不出调用方项目。

"你不需要知道采集器长什么样，调用接口就有数据"——这是它与"每个项目各写一套爬虫"的本质区别。

---

## 二、三条核心目标（用户原话沉淀，2026-08-28）

### 目标 1：基建产品——可挂载的 HTTP 服务公共平台

- 提供**挂载的 HTTP 服务**：内置信息采集器 + 路由表，任何人/任何应用都可以连接并使用
- 通过 HTTP 接口：提交任务 / 查状态 / 拉结果 / 收回调，统一 JSON 协议
- 采集器可**平台外挂载**（extra_dirs），加源不改内核——平台仓零改动
- 消费方不关心采集器内部，API 稳定不变

### 目标 2：完全解耦 + 数据隐私（核心思想）

- **完全解耦**：平台只留存采集器 + 平台自身数据，不含任何业务项目的代码或数据
- **数据隐私**：采集数据对客户完全保密——**数据不出调用方自己的项目**
- **分流铁律**：涉业务机密的数据源必须客户端挂载（业务项目内），平台物理不接触
- 平台内存态存储（零持久化），进程重启即清——不留下任何业务痕迹

### 目标 3：轻量，内核小

- 纯 Python（FastAPI），核心 ~12k 行，无重依赖
- 内存态任务/结果/去重，无数据库引擎、无文件句柄、无临时文件
- 单服务即可运行，部署成本趋近于零

## 三、核心概念界定（防歧义）

| 概念 | 定义 | 现状 |
|---|---|---|
| **挂载** | 采集器以目录外挂（extra_dirs），路由表登记即可用，平台仓零改动 | ✅ config.d + collectors_extra_dirs |
| **完全解耦** | 平台不含业务代码/数据；业务源走客户端挂载 | ✅ 平台仓纯净 |
| **零持久化** | 全部状态在进程内存，TTL 过期 + 交付即清，重启即清 | ✅ 内存态（TTL 1h / 429） |
| **分流铁律** | 通用 ? 多项目用 → 内置；涉业务机密 → 客户端 | ✅ 铁律，public 仓 |
| **交付即清** | 结果被消费后立即释放，不留痕 | ✅ /items 消费即清 |

## 四、当前基础盘点

### ✅ 已实现
- HTTP API：`POST /v1/collect`（异步）+ `/collect/sync`（同步）+ 任务查询 + 结果拉取（:9000）
- 任务队列 + 内存态存储（TTL 1h / 429 退避 / 交付即清）
- 内置 11+ 采集器可用：官方源（白宫/欧委会/美联储/SEC/NVIDIA/GlobeNewswire）、学术（arXiv）、行业（ADAS 季刊）、合规（SFDA/SASO/GSO/国标/ASTM）、高难源（东财/巨潮 CDP 绕 WAF、BOSS wapi+浏览器渲染）
- 采集器外挂机制（extra_dirs 多目录挂载，config.d 路由表）
- APICollector 基类（API_SPEC 声明式，arxiv 改造验证实例）
- 健康巡检 `intel check` + cron 快照/预警（18:30/18:45，command payload）
- BOSS 采集器：wapi 直连主路线 + 自适应频率控制（指数退避 + 熔断）

### ❌ 待建/待完善
- 多实例部署（水平扩展）
- 认证机制（目前内网/本地单点信任）
- 采集器生态扩展（更多通用源 + 客户端示范）
- 路由表管理界面（目前文件配置）
- 对外文档与接入示例完善（产品书已有，SDK/示例待补）

## 五、产品价值主张（对客户说）

| 客户痛点 | BriefNexus 答案 |
|---|---|
| 每个应用都要自己写爬虫/对接源，重复造轮子 | 调一个 HTTP 接口，复用现成采集器 |
| 业务敏感数据不敢过第三方平台 | 采集器挂载自己项目，数据不出门 |
| 加新数据源要改平台代码，牵一发动全身 | 平台外挂载新采集器，内核零改动 |
| 多项目各自维护采集逻辑 | 一套平台，多项目即连即用 |
